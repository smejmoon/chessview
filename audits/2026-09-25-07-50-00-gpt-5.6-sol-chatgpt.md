## Findings

### Explorer rate-limit failures are retried as normal discovery work

**Evidence:** In `src/explorer.js:loadExplorer`, every non-401 HTTP failure becomes `throw new Error(\`Lichess explorer returned ${response.status}\`)`; there is no 429-specific cooldown. In `src/explorer.js:discoverForViewport`, branch failures are caught and the loop immediately advances to the next frontier item, so a 429 on one branch does not stop subsequent Explorer requests. `src/main.js:recenter` starts a new `refreshDiscovery()` without cancelling an older discovery, so separate discovery runs can also coexist. Lichess's current API guidance says clients should make one request at a time and, after HTTP 429, wait a full minute before resuming API usage.

**Why it matters:** Once Lichess starts throttling, Chessview can keep sending requests during the required cooldown, prolonging the throttled state and turning normal graph navigation into repeated 429 failures. A rapid recenter can additionally leave obsolete background discovery consuming request capacity for positions the user no longer views.

**Suggested next action:** Put all Explorer network fetches behind one global serialized request controller. On 429, suspend that controller for at least 60 seconds before any further Explorer call; stop or invalidate stale discovery work when the center changes, while still allowing cached IndexedDB reads to render immediately.

**Confidence:** high

### Explorer refresh does not reconcile persisted outgoing edges

**Evidence:** `src/explorer.js:loadExplorer` builds an `edges` array from the latest response and calls `putEdges(edges)`. `src/db.js:putEdges` only `put()`s those records; it never removes existing non-manual edges for that source that are absent from the new response. Conversely, when a previously manual edge appears in a later Explorer response with the same `source|uci|target` id, that `put()` replaces the record with `manual: false`.

**Why it matters:** The persisted graph can diverge from the current Explorer snapshot. A move that falls out of the returned move set can remain indefinitely and still participate in `getOutgoing()`/neighborhood selection with stale `share` and `qualifies` values. A below-threshold move the user explicitly explored can also lose its manual marker after refresh, changing whether it remains selectable as a known branch.

**Suggested next action:** Reconcile each source position transactionally when Explorer data refreshes: replace the source's Explorer-derived edge set, delete stale Explorer edges, and preserve manual-discovery state independently (or merge it with an OR rule) rather than letting a network refresh erase it. Add tests for a move disappearing between snapshots and for a manual edge later appearing in Explorer data.

**Confidence:** high

### OAuth callback failure paths can become sticky

**Evidence:** `src/auth.js:completeLichessAuth` removes callback parameters when Lichess returns an explicit OAuth `error`, but the state-mismatch branch throws without cleaning `code`/`state` from the URL or clearing the stored verifier/state/redirect values. Token-exchange failures likewise throw before callback cleanup. On reload, the same callback parameters are therefore processed again instead of starting a fresh authorization attempt.

**Why it matters:** A lost `sessionStorage` entry, cross-tab state mismatch, or failed token exchange can leave the current position repeatedly failing authentication on reload. The error tells the user to try signing in again, but the callback state has not been consumed/reset to make that retry happen automatically.

**Suggested next action:** Treat callback success and terminal callback failure as one-shot states. On mismatch or failed exchange, remove OAuth callback parameters, clear the stored PKCE transaction values, retain the chess `fen` query parameter, and expose or automatically initiate a clean retry path.

**Confidence:** high

### Authentication and Explorer behavior have no regression tests

**Evidence:** The complete `test/` tree contains only `test/graph.test.js`, which imports and tests `src/graph.js`. There are no automated tests for `src/auth.js`, `src/explorer.js`, IndexedDB reconciliation, HTTP status handling, OAuth callback cleanup, or discovery cancellation/rate-limit behavior. `package.json` runs only `node --test`, so no other browser/integration test suite is wired into CI.

**Why it matters:** The application's live-data path now depends on several non-trivial branches—PKCE generation/callback validation, token exchange, 401 handling, 429 handling, persistence, and progressive discovery—but CI can remain green while those paths are broken. The recent authentication change and observed 429 behavior are exactly in code that the deterministic suite cannot currently detect.

**Suggested next action:** Add focused tests around the public boundaries: mock fetch/storage for OAuth success, denial, state mismatch, token-exchange failure, 401 and 429; use an IndexedDB test implementation for edge reconciliation; and add a discovery test that proves stale work stops and requests remain globally serialized. Keep live Lichess calls out of deterministic CI.

**Confidence:** high

### The current plan documents the retired Explorer contract

**Evidence:** `docs/PLAN.md` under **Technical choices** states: `The browser calls https://explorer.lichess.ovh/lichess directly.` Current implementation instead uses `https://explorer.lichess.org/lichess` in `src/explorer.js` and requires a bearer token through `src/auth.js`. The same plan's discovery model describes fetching Explorer statistics but never includes the now-required OAuth/PKCE authorization step.

**Why it matters:** `README.md` points readers to `docs/PLAN.md` for the v1 requirements and implementation decisions, so a maintainer following the repository's own plan is directed toward an endpoint and unauthenticated flow that no longer match the running application. That can cause future maintenance to reintroduce the 401 failure or omit auth-related requirements from design changes.

**Suggested next action:** Update the plan's technical choice and discovery sequence to name the authenticated `.org` Explorer endpoint, browser OAuth2 PKCE flow, token lifecycle/error behavior, and rate-limit obligations. Keep historical endpoint information only if it is explicitly marked historical.

**Confidence:** high
