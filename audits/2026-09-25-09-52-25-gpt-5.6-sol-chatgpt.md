## Findings

### Preview slug mapping is not collision-free or path-length safe

**Evidence:** In `.github/workflows/pages.yml` → `Determine Pages target`, branch names consisting only of `[A-Za-z0-9._-]` are used verbatim as `slug`. Branch names containing any other permitted Git ref character are normalized and get only the first eight hex characters of `sha256(branch)` appended; the preview target is then `previews/${slug}`. This namespace is not injective. The valid branch `a/b` normalizes to `a-b-c14cddc0`, while the distinct valid branch `a-b-c14cddc0` is already regex-safe and is therefore left unchanged, so both target `previews/a-b-c14cddc0`. `git check-ref-format --branch` accepted both names. The same logic is also unbounded: a valid ref made from two 200-character components separated by `/` normalized to a single 410-character directory component, which the current Linux filesystem rejected with `File name too long`.

**Why it matters:** Two task branches can overwrite the same preview subtree, violating the required preview isolation. Sufficiently long valid branch names cannot publish at all. Both failures occur before the workflow's later `PAGES_TARGET` guard, because that guard verifies only the `previews/*` prefix, not uniqueness or filesystem viability.

**Suggested next action:** Make the preview directory mapping bounded and collision-resistant for every branch, not only branches that require character replacement. A small approach is a truncated readable prefix plus a sufficiently long hash of the full branch name for all non-main branches, with tests for the concrete collision pair and long multi-component refs.

**Confidence:** high

### Deployment safety branches have no regression tests

**Evidence:** `.github/workflows/pages.yml` adds non-trivial behavior for production-vs-preview target selection, branch sanitization, production preservation of `previews/`, preview-only replacement, fail-closed root/subtree guards, and aggregate-tree publication. `package.json` defines `npm test` as `node --test`. The complete `test/` tree at the audited revision contains only `auth.test.js`, `db.test.js`, `explorer.test.js`, `graph.test.js`, `request-gate.test.js`, and `roots.test.js`; none executes or asserts the Pages workflow or its shell logic. Actions run `36119965485` succeeded on `pages-previews`, which exercises only the preview path for an already regex-safe branch. It does not exercise the `main` production-preservation path, a branch requiring sanitization, the collision/length cases above, or the safety guards under adverse inputs. The collision defect therefore passes the current required test/build gate.

**Why it matters:** The workflow's highest-impact guarantees are implemented only as untested shell branches. A regression can pass `npm test`, build successfully, and reach the publisher despite breaking production preservation or preview isolation—the exact safety properties this change is intended to establish.

**Suggested next action:** Put the deterministic target/slug and tree-update logic behind a small testable script or lightweight shell harness, and run those tests before publication. Cover at minimum: production preserves an existing `previews/` tree; preview cannot modify production root; unsafe branch names map uniquely; long valid refs stay within a safe component bound; and the production/preview guards fail closed on wrong targets.

**Confidence:** high

## Operational caveat

The prospective landed workflow protects previews from later production publishes, but the currently deployed review preview is still in a bootstrap window until this change reaches `main`. Current `main` still uses the previous workflow, which force-pushes `dist` as the entire `gh-pages` branch and uses a different concurrency group. A `main` publish before this workflow lands can therefore erase the active branch preview. This is a property of the pre-landing base workflow, not an additional defect in the prospective landed change.
