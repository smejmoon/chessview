## Findings

### UI composition is an implicit multi-writer DOM protocol

**Evidence:** `index.html` starts three independent application modules: `src/main.js`, `src/root-pgn.js`, and `src/eval-ui.js`. `src/main.js#renderShell` replaces `#app` wholesale with `app.innerHTML` and owns the primary scene/rail render. `src/root-pgn.js` separately installs a `MutationObserver` on `#app`, rewrites satellite positions and `#edges`, reparents Root rows, identifies domain edges by reading rendered label text, persists transposition-derived graph data, and asks the main renderer to refresh by dispatching a synthetic `resize` event. `src/eval-ui.js` installs another `MutationObserver`, moves/replaces rail DOM, maps connector paths to satellites by array index in `decorateConnectorQuality`, and navigates by editing history then dispatching a synthetic `popstate`. There is no explicit API or stable edge identifier at the shared DOM boundary.

**Why it matters:** domain state, rendering, graph enrichment, navigation, and evidence decoration can invalidate each other through markup order or timing rather than an explicit contract. A harmless render change such as reordering satellites or connectors can silently attach quality/rarity styling to the wrong edge because `eval-ui.js` pairs two DOM collections by index. A label change can alter edge selection in the Root/eval decorators. Because graph persistence is also initiated from the Root DOM decorator, whether model data is enriched depends on presentation state. This is a high-coordination boundary with three writers and no owner.

**Suggested next action:** make one application/controller layer own rendering and navigation. Have Root/transposition and evaluation modules return explicit data keyed by stable node/edge IDs into a scene/view model; let the renderer consume that model once. Move graph enrichment out of DOM observers into the discovery/model layer, and replace synthetic `resize`/`popstate` signaling with explicit application events or function calls.

**Confidence:** high

### Branch-balanced discovery collapses each Line to one descendant spine

**Evidence:** `docs/PLAN.md` §Graph discovery model requires Chessview to recursively inspect qualifying branches while useful slots remain; §Branch-balanced selection says remaining capacity is spent round-robin across Lines while avoiding excessive breadth from a bushy branch. In `src/explorer.js#discoverForViewport`, after a position is loaded, qualifying children are sorted but only `next[0]` is appended to the frontier. The other qualifying children of that position are never scheduled. `src/graph.js#chooseNeighborhood` repeats the same shape at selection time: each first-level Line has one queue whose `current` position is advanced to a single unseen child, so the queue follows one chain rather than retaining a frontier of sibling continuations. `test/explorer.test.js` covers cancellation but has no case where a discovered Line has multiple qualifying children and spare budget.

**Why it matters:** on a branching continuation, qualifying moves beyond the single chosen child can remain undiscovered and therefore cannot become visible Lines, future Roots, or transposition evidence. The behavior is deterministic, but it is not the branch-balanced recursive exploration described by the product authority; it turns every first move into a preferred spine.

**Suggested next action:** represent each first-level Line with a deterministic frontier of qualifying descendants instead of a single `current` node. Allocate discovery/visible slots round-robin across those frontiers, retaining siblings for later capacity. Add a test where one Line produces two or more qualifying children and assert that spare budget eventually reaches more than the first child.

**Confidence:** high

### Lichess evidence traffic bypasses the shared request policy and hides failures

**Evidence:** `docs/PLAN.md` §Technical choices says Explorer network requests are globally serialized and that HTTP 429 pauses all new Explorer traffic for at least 60 seconds. `src/explorer.js` enforces this through its module-global `requestGate`. `src/eval.js`, however, calls both `https://explorer.lichess.org/masters` and `https://lichess.org/api/cloud-eval` with direct `fetch` calls. The official Lichess OpenAPI classifies `/masters` as an **Opening Explorer** endpoint (`lichess-org/api`, `doc/specs/tags/openingexplorer/masters.yaml`, blob `8df692cb9b213cdc1bda51e921270d74de0e48c5`). Its top-level rate-limit contract says to make only one request at a time and, after a 429, normally wait a minute and reduce request frequency (`doc/specs/lichess-api.yaml`, blob `737038e8b17f06a6ca895c3afa5ab64113caeead`). `src/eval-ui.js#decorateLineRail` explicitly hydrates moves in `Promise.all` batches of four, so uncached cloud-eval requests can overlap. `loadCloudEval` and `loadMasters` catch request failures and return cached data or `null`; only cloud-eval 404 is distinguished as a true absence.

**Why it matters:** the product's network invariant is enforced for rated Explorer but not for Masters evidence, even though Masters is part of Opening Explorer, and cloud-eval calls can overlap those requests. A 429 or network/API failure in the evidence layer does not activate the shared cooldown and is rendered like missing evidence. That can create repeated pressure on Lichess while making a transport failure look like a chess-data fact (for example, “eval unavailable” or absent human markers).

**Suggested next action:** introduce one Lichess transport/scheduler used by rated Explorer, Masters, and cloud evaluation. Centralize serialization, endpoint-specific caching, 429 cooldown/backoff, cancellation for obsolete centers, and explicit outcomes for `not found` versus `request failed`. Add a cross-client test that starts Explorer/Masters/eval work together and proves the shared concurrency/cooldown contract.

**Confidence:** high

### Product-critical browser composition has no automated contract test

**Evidence:** the complete `test/` tree contains tests for auth, DB reconciliation, eval calculations, explorer cancellation/401, graph selection, Pages targets, PGN formatting, request gating, Roots selection, and transposition enumeration. No test imports or exercises `src/main.js`, `src/root-pgn.js`, or `src/eval-ui.js`, the three modules that compose the browser product. `docs/PLAN.md` §Test plan also promises URL round-tripping, but the suite never directly exercises `positionFromUrl`/`positionUrl` or history/view round-tripping. The DOM-only contracts from the first finding—Root tree reconstruction, linked hover, connector/evidence association, synthetic navigation, and observer-driven transposition refresh—therefore have no automated failure signal.

**Why it matters:** the highest-coupling part of the application can regress while every current unit test stays green. In particular, tests establish the correctness of graph/eval primitives but not that the browser composes those primitives into the intended Root/Line map, Rail, and navigation behavior. This makes UI refactors risky and allows contract drift between `docs/PLAN.md` and the actual app shell.

**Suggested next action:** after establishing an explicit scene/render boundary, add a small deterministic browser-composition test surface that covers Root and Line rendering, stable edge-to-board/evidence association, recenter/history/view behavior, and one transposition-enrichment refresh. Add direct URL round-trip tests immediately because those helpers are already pure enough to test without a browser harness.

**Confidence:** high

### CI resolves a fresh transitive dependency graph on every run

**Evidence:** the complete repository tree contains `package.json` but no `package-lock.json` or other lockfile. Direct dependencies are pinned in `package.json`, while `.github/workflows/pages.yml` installs with `npm install` before tests and the production build. The same workflow then publishes the resulting `dist/` to `gh-pages`.

**Why it matters:** exact direct versions do not pin their transitive dependency graph. The same Chessview commit can therefore test and build against different transitive versions on different days, including the artifact published to production or a branch preview. That weakens reproducibility, makes rollback evidence less reliable, and makes a dependency-registry change capable of breaking an otherwise unchanged branch.

**Suggested next action:** commit the npm lockfile generated for the supported Node/npm toolchain and switch CI to `npm ci`, so the tested dependency graph is the graph that is built and published.

**Confidence:** high
