## Findings

### PLAN re-home left live backlog pointers aimed at removed sections

**Evidence:** `backlog/2026-09-25-branch-balanced-discovery.md` §Because points to `docs/PLAN.md` sections “Graph discovery model” and “Branch-balanced selection”. `backlog/2026-09-25-browser-composition-boundary.md` §Because points to `docs/PLAN.md` sections “Product requirements” and “Test plan”. The current `docs/PLAN.md` no longer contains any of those sections; it explicitly re-homes detailed contracts to `docs/components/` under §Components and §Maintaining the plan. The first outcome's relevant current owner is `docs/components/discovery.md`; the second's is `docs/components/interface.md`.

**Why it matters:** both backlog entries are live trackers whose rationale now tells a cold reader to inspect headings that no longer exist. That forces rediscovery of the governing requirement and makes future backlog sync/close work vulnerable to using the wrong contract. Boundary investigation confirms this is a companion-reference miss from the PLAN re-home, not a reason to restore the removed PLAN sections or change the outcomes themselves.

**Suggested next action:** update the two backlog `Because:` passages to point directly to the relevant component file and stable section title(s), preserving the same rationale.

**Confidence:** high

### LichessGateway's behavioral contract has two owners and an over-broad “all network access” invariant

**Evidence:** `docs/PLAN.md` §Maintaining the plan says linked component documents own detailed requirements. `docs/components/lichess-access.md` §Network boundary then defines the gateway's serialization, 429 cooldown, cancellation, and transport-outcome requirements. `docs/architecture/lichess-gateway.md` §Ownership independently maintains the same behavioral list, while `rules/lichess-gateway.md` says that architecture “governs” the boundary and forbids “direct Lichess network access outside `LichessGateway`”. Meanwhile `src/auth.js#beginLichessAuth` intentionally performs browser navigation to `https://lichess.org/oauth` with `window.location.assign(...)`; that navigation is Lichess network access but is not, and cannot usefully be, a queued `fetch` through the gateway.

**Why it matters:** a behavioral policy change currently requires coordinated semantic edits in both the component requirement and architecture authority, despite the plan declaring one detailed owner. The literal always-loaded rule also makes the necessary OAuth authorization navigation appear architecturally forbidden. This can send future work toward changing correct auth code merely to satisfy an over-broad instruction. Boundary investigation confirms the defect is in the documentation/rule ownership and scope, not in the existing OAuth navigation or gateway implementation.

**Suggested next action:** choose one maintained owner for gateway behavior. A minimal split is to keep observable request-policy requirements in `docs/components/lichess-access.md`, keep `docs/architecture/lichess-gateway.md` to dependency/ownership direction, and scope the architecture/rule invariant to application-issued Lichess API/transport requests while explicitly leaving browser OAuth authorization navigation outside that scheduler.

**Confidence:** high

### “Cross-client” tests exercise an isolated gateway, not the clients that must share it

**Evidence:** `docs/components/lichess-access.md` §Verification requires cross-client serialization between rated Explorer, Masters, cloud evaluation, and other gateway users. `test/lichess-gateway.test.js` creates a fresh `createLichessGateway()` and passes string labels (`rated-explorer`, `masters`, `cloud-eval`) directly to `gateway.request`; it never invokes `src/auth.js`, `src/explorer.js`, or `src/eval.js`. The complete `test/` surface separately tests auth, Explorer, eval loading, request-gate behavior, and gateway behavior, but contains no test that concurrently exercises those real client modules through the singleton `lichessGateway`. The production modules currently do import that singleton, so the implementation is wired correctly today; the existing “cross-client” test would nevertheless keep passing if one client later reverted to direct `fetch`.

**Why it matters:** application-wide serialization is the central externally constrained invariant this change introduces. The suite pins the scheduler primitive but not the integration that makes it application-wide, so the exact regression the architecture forbids can land green. Boundary investigation confirms this belongs at the integration/conformance test boundary rather than requiring more scheduler machinery.

**Suggested next action:** add the smallest deterministic integration or conformance test that fails when any real Lichess-backed client bypasses the shared gateway, and that demonstrates overlapping client requests are serialized by the one production boundary.

**Confidence:** high

### Explicit evidence-request failures are collapsed again by downstream consumers

**Evidence:** `src/eval.js#loadCloudEval` and `#loadMasters` now preserve an uncached failed request as a tagged `{ requestFailed: true, ... }` value, and `test/eval-loading.test.js` pins that distinction at the loader boundary. But `src/eval.js#positionEvaluation` treats that tagged value the same as any unusable/no evaluation and returns `null`; `humanMoveStats` / `humanMismatch` likewise reduce a Masters failure to no usable move data and ultimately `null`. The unchanged `src/eval-ui.js` never calls `isEvidenceRequestFailure`: center evaluation renders `eval unavailable`, move decoration can say `No adequate cloud eval`, and failed Masters evidence produces the same absence of mismatch marker as ordinary no-mismatch/no-data cases. `docs/components/evidence.md` §Human evidence says failure to fetch Masters or engine evidence must not be interpreted as evidence that no disagreement or evaluation exists, and `docs/components/lichess-access.md` §Cache and failure semantics says failure remains explicit when no evidence exists.

**Why it matters:** the change successfully distinguishes failure from absence at the network/domain loader boundary, then loses that distinction before the evidence/presentation boundary that consumes it. In particular, absence of a human-mismatch marker can mean either “no material mismatch” or “Masters evidence could not be obtained”. Boundary investigation confirms the gateway and loaders already do their part; the unresolved behavior is downstream evidence-state handling, not transport scheduling.

**Suggested next action:** preserve a discriminated unavailable/failure state through evidence helpers and presentation (or explicitly narrow the documented requirement if the product intentionally needs the distinction only at the loader API), and add a consumer-level test that cannot pass when request failure and genuine absence/no-mismatch collapse to the same state.

**Confidence:** high
