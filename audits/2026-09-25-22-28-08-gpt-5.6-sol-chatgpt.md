## Findings

### Settled check survives into a pending generation

**Evidence:** `docs/components/interface.md` §Requirements defines the check as the settled state of the *current* view generation. In `src/view-cycle.js`, `start()` begins a new generation with `present(hasSettled ? 'check' : 'hidden')` and only schedules `updating` after 180 ms; `begin()` does the same when visible work reopens a settled cycle. `test/view-cycle.test.js` explicitly expects the persistent check to remain visible after later work begins, until the delayed timer fires.

**Why it matters:** for the first 180 ms after navigation or reopened visible work, the UI can display the check whose meaning is “Current view finished updating” while the current generation already has pending work. That makes the subtle readiness signal semantically stale exactly at the transition where the user relies on it.

**Suggested next action:** separate “pending but too fast to show text” from “settled.” On cycle start/reopen, remove the settled check immediately (or replace it with a pending mark) while delaying only the `Updating…` text/animation. Pin navigation from a previously settled generation in the lifecycle tests.

**Confidence:** high.

### Contributor exceptions are counted as Ready without an explicit failure state

**Evidence:** `docs/components/interface.md` §Requirements says a view may settle after failure only when that failure is explicit. `src/eval-ui.js` `decorate()` catches any decoration exception with `console.error(...)` and then, in `finally`, reports the `evidence` task settled. `src/root-pgn.js` `decorateForView()` does the same for the `structure` task. `src/main.js` treats those settlement reports identically to successful completion when deciding `Ready`.

**Why it matters:** an unexpected evidence or Root-composition failure can leave visible data/decorations incomplete while the top bar still transitions to `✓ Ready`; the only failure signal is the developer console. Transport failures handled as explicit evidence values are not the problem here—the broad component-level catch path is.

**Suggested next action:** make contributor completion carry a terminal outcome, and only count a failed contributor as settled after the current view exposes an explicit failure state (for example a scoped unavailable marker/toast). Add a test that forces a contributor exception and requires both terminal readiness and a visible failure indication.

**Confidence:** high.

### Obsolete evidence work is generation-stale but not request-cancelled

**Evidence:** `src/eval-ui.js` guards stale results by checking `currentCenter()` after awaits, but its calls to `loadCloudEval(...)` and `loadMasters(...)` do not pass an `AbortSignal` in `evidenceForEdge()`, `decorateLineRail()`, `decorateCenter()`, or target-eval hydration. Current `src/eval.js` already accepts `{ signal }` and passes it to `LichessGateway`. The changed `docs/components/lichess-access.md` §Network boundary requires obsolete queued work to be preventable from reaching the network, while `docs/components/interface.md` says background work that cannot change the current view must not block readiness. The same Lichess component requires application-wide one-at-a-time request scheduling.

**Why it matters:** after recentering, old evidence code will ignore its results, but already queued cloud-eval/Masters requests remain live. Because the gateway is globally serialized, those obsolete requests can still be sent ahead of evidence for the new generation and delay the new view from settling. The generation token prevents stale UI mutation, not stale network work.

**Suggested next action:** keep cancellation at the controller/evidence seam rather than changing `LichessGateway`: give each View Cycle a cancellation signal and pass it through the evidence contributor to `loadCloudEval`/`loadMasters`; abort the old generation on recenter/view change. Add a gateway/client test where obsolete evidence is queued before current-view evidence and prove it never reaches `fetch`.

**Confidence:** high.

### View-cycle tests stop at the pure state machine

**Evidence:** `docs/components/interface.md` §Verification requires current-view settlement to wait for every visible contributor, reject stale generations, preserve fast cached behavior, and count explicit failures as terminal. `test/view-cycle.test.js` exercises only `createViewCycleController`; it does not load `src/main.js`, `src/eval-ui.js`, or `src/root-pgn.js`, does not exercise the `VIEW_RENDERED_EVENT` / `VIEW_WORK_SETTLED_EVENT` wiring, and does not assert the rendered top-bar state. The repository test command is plain `node --test` and the current dependency set has no browser/DOM harness.

**Why it matters:** production regressions such as a contributor never reporting settlement, reporting the wrong token, the status element not reflecting controller state, or a navigation path failing to start a new cycle can all leave these unit tests green. The most failure-prone part of the feature is the composition wiring, not the Map/token primitive in isolation.

**Suggested next action:** add the smallest browser/DOM-level contract test around the real main/contributor seam: start a view, hold each contributor independently, navigate to supersede a generation, inject one explicit failure, and assert `Updating… → Ready → ✓` only from the current generation. Keep the pure controller tests as the lower-level suite.

**Confidence:** high.
