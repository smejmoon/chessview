## Findings

### Budget saturation drops zero-cost convergence relationships

**Evidence:** In `src/graph.js::chooseNeighborhood`, the outer loop is guarded by `visible.boardCount() < max`, and each frontier iteration breaks immediately when `visible.boardCount() >= max`. `chooseRootNeighborhood` has the same pair of budget gates. By contrast, `src/visible-graph.js::addNode` deliberately checks for an existing canonical node *before* enforcing `nodes.length >= max`, so adding family membership and an additional relationship to an already-visible node is designed to cost no board slot. A concrete Line trace with the target's own convergence fixture and `max: 3` selects `a`, `b`, then `shared` from Line A; board count becomes 3 and the inner guard breaks before Line B's `b -> shared` candidate can be recorded. The changed test `Line convergence keeps one board and every visible family relationship` uses `max: 4`, so Line B reaches `shared` before the fourth board fills the budget and the defect is not exercised. `test/roots.test.js` likewise tests Root convergence with `max: 8`, not at the saturation boundary. This contradicts `docs/components/discovery.md` §Root frontier policy boundary, which says a later frontier reaching an already-visible canonical position consumes no additional board slot and merges its additional edge/family, and it contradicts the changed backlog's `Complete:` claim that every visible relationship/family reaching a canonical board is retained while that board is counted once.

**Why it matters:** At exactly the responsive board limit, the map can show the canonical converged board while silently dropping another Line/Root relationship and family membership that reaches it. The new composition model therefore still makes graph meaning depend on traversal order and remaining board capacity at the boundary it was introduced to remove. A shared descendant can also retain only the family processed before the last slot fills, so downstream family-specific presentation can become incomplete.

**Suggested next action:** Change selection termination so reaching the board cap prevents only creation of *new* canonical boards; still drain/accept pending candidates whose target node is already visible so their relationships and family memberships can be merged without spending capacity. Add deterministic tight-budget cases for both Lines and Roots (including a convergence that lands exactly on the final board slot) and a shared descendant case that proves all converged families propagate after the cap is reached.

**Confidence:** high

### The backlog `Sync:` contract was weakened

**Evidence:** `backlog/2026-09-26-visible-graph-composition.md` §`Sync:` now says only: “After any implementation or verification step that changes what remains, and before ending an implementation pass, rewrite this entry around factual remaining work rather than accumulating progress history.” The pre-change entry carried the standard Close gate. The governing Strake `skills/backlog/SKILL.md` §Format says every open entry's final `Sync:` passage is fixed and must be exactly the standard text, including: “If `Complete:` is satisfied, run Backlog Close. If Close cannot pass its normal gates, leave the entry open with the blocking condition explicit.”

**Why it matters:** An agent picking up this live backlog entry no longer receives the required Close action and failure gate from the entry itself. That weakens the lifecycle contract exactly where the Backlog owner requires uniform wording, allowing a completed outcome to remain open or be handled inconsistently.

**Suggested next action:** Restore the `Sync:` passage verbatim from Strake `skills/backlog/SKILL.md` §Format. Keep any task-specific maintenance wording elsewhere only if it states a distinct requirement rather than replacing the fixed lifecycle passage.

**Confidence:** high

### The backlog claims tests ran, but the target commit only ran the Pages build

**Evidence:** The changed backlog entry's `Complete:` passage says: “The branch Pages workflow, including its test/build steps, succeeds on the selection checkpoint.” For target commit `c0f4b0b0b67815a629c304e63c7021b80680145f`, the only workflow run found for that head SHA is `Build and publish Pages` run `36241135798`, which succeeded. Its job steps include dependency installation, Pages-target determination, `Build static site`, and publication; there is no test step. `.github/workflows/pages.yml` confirms that `Build static site` runs `npm run build`, while `package.json` defines `build` as `vite build` and `test` separately as `node --test`. Deterministic tests live in `.github/workflows/ci.yml`, but that workflow triggers on pushes to `main`, pull requests targeting `main`, or manual dispatch; the audited `vivi` target commit had no CI run in the inspected head-SHA workflow evidence.

**Why it matters:** The durable backlog text records the new convergence tests as execution-verified when the cited branch workflow did not execute them. That can make later work treat selection behavior as proven even though only compilation/build and preview publication were established for the exact target commit.

**Suggested next action:** Run the deterministic test suite against the exact audited implementation through an authoritative execution path, then rewrite the verification statement to name only what actually ran and passed. Until then, retain the successful Pages build/preview claim separately from test verification.

**Confidence:** high
