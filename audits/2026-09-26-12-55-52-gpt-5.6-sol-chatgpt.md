## Findings

### Merge state conflates ordinary graph degree with convergence

**Evidence:** `src/visible-graph.js:addRelationship` appends each visible relationship id to both endpoint nodes and then sets `node.merge` when `node.relationships.length > 1`. A normal interior Line node therefore becomes `merge: true` as soon as it has one incoming and one outgoing visible edge, even though no transposition converged there. `src/graph.js:chooseRootNeighborhood` repeats the same semantic collapse in its compatibility projection by building `node.edges` from every incident relationship and then setting `node.merge = node.edges.length > 1 || node.branches.length > 1`. For an ordinary Root chain, a node with one edge toward the Nodus and one edge farther upstream is consequently marked as a merge. This conflicts with the interface contract, where merge state denotes visible transposition convergence and controls merge-specific presentation such as multiple downstream connectors and ambiguous move cues. The added tests cover true convergence but contain no negative assertion that an ordinary degree-two continuation remains non-merge.

**Why it matters:** the next refactor step explicitly moves rendering onto this projection. If rendering trusts `node.merge`, ordinary interior boards will be eligible for transposition styling/behavior even though only one path reaches them. In Roots, the compatibility `edges` array also loses the old directional meaning of “visible downstream edges” by mixing upstream and downstream incident edges, which can make merge/cue logic count the wrong relationships.

**Suggested next action:** define merge from directional convergence rather than total incident degree — for example, multiple visible incoming relationships in Lines, multiple visible downstream relationships / families in Roots, or an explicit convergence membership computed by the selector. Keep compatibility `edges` directional if it remains temporarily. Add negative tests for a simple multi-ply Line and Root chain proving their interior nodes are not merges, alongside the existing positive transposition tests.

**Confidence:** high

### A converged Line relationship exposes only one family’s share

**Evidence:** `src/visible-graph.js:addRelationship` stores one scalar `lineShare` on a relationship. When the same graph edge is later reached by another Line family, the existing relationship merges the new family into `existing.families` but retains the original `lineShare` unless it was null. `test/graph.test.js` demonstrates the converged descendant case with `shared -> after`: the relationship belongs to both `line-a` and `line-b`, but the test checks only the merged family list, not two inherited first-move shares. The two families have different first-move shares (`0.6` and `0.25`). ChessView’s interface contract requires every deeper segment belonging to a Line to inherit that Line’s first-move share, and the backlog explicitly says per-family `lineShare` is presentation state the visible projection must preserve.

**Why it matters:** once rendering is changed to iterate explicit relationships, a consumer that uses `relationship.lineShare` has a semantically false value for a shared relationship: `shared -> after` cannot simultaneously represent both Line widths with one scalar. The family records still retain both source shares globally, so the information is recoverable by a join, but the relationship contract itself presents a singular value that ceases to be valid exactly at the convergence case this refactor is meant to model.

**Suggested next action:** make family-specific relationship membership explicit (for example, relationship memberships carrying `{ family, lineShare }`) or remove the singular `relationship.lineShare` and require resolution through family identity. Add a test for the shared descendant relationship that proves both inherited Line shares remain addressable for that same graph edge before wiring the renderer to it.

**Confidence:** high
