## Findings

### Same-target Root restart can inherit an obsolete caller's cancellation

**Evidence:** `src/nodus-structure.js` `expandCurrentRootTranspositions()` caches an in-flight promise in `expandingTargets` by target and returns that same promise to later callers. The cached promise closes over the first caller's `signal` and calls `throwIfAborted(signal)` after awaited work. `src/nodus-controller.js` `#startView()` aborts the previous run before every refresh/restore/mode/navigation restart; a new Roots composition for the same center can therefore join the old cached promise after its owning signal has been aborted. When that promise rejects with `AbortError`, the new current run reaches `#composeCurrent()`, whose catch treats any `AbortError` as a non-result and returns `false`, leaving the new view at the `structure: loading` state installed by `#startView()`. The removed base `src/root-pgn.js` shared the same-target expansion promise without binding it to a caller AbortSignal, so this first-caller cancellation coupling is introduced by the refactor. `test/nodus-controller.test.js` does not exercise a shared same-key structure operation whose first caller is superseded.

**Why it matters:** A refresh or other same-center Roots restart during transposition preparation can strand the current view in structural loading until some later command starts another cycle. That violates the product requirement that current-view structural work reach a terminal outcome and makes an obsolete revision capable of preventing the replacement revision from settling.

**Suggested next action:** Make shared Root transposition preparation independent of any one caller's revision lifetime, or give callers independent participation in the shared work; then add a deterministic regression where caller A starts same-target preparation, caller B supersedes A, A becomes obsolete, and B still reaches a terminal ready/failed structure without requiring another command.

**Confidence:** high

### A new loading view reuses the previous view's status timer

**Evidence:** `src/view-status.js` `update()` resets its transition counter and timers only when the string `view.structure.status` changes. `src/nodus-controller.js` `#startView()` creates a fresh current-view revision and publishes `structure: loading` for every new view. If a Lines view is already `loading` and another view/restart begins while it is still loading, the presenter receives `loading → loading`, does not create a new transition, and retains both the prior presentation (`updating` may already be visible) and any remaining delay timer. The removed base `src/view-cycle.js` `start()` cleared timers and incremented a cycle identity on every new view regardless of whether the visible status string changed. `test/view-status.test.js` covers `ready → loading` but has no case for a new view beginning while the prior view is still `loading`.

**Why it matters:** The replacement view can show `Updating…` immediately because the superseded view was already showing it, or after only the remainder of the superseded view's 180 ms delay. This breaks the requirement that readiness treatment be scoped to the current view generation and can reintroduce the distracting loading flash that the delayed treatment is meant to avoid for quickly settling work.

**Suggested next action:** Give the status presenter an explicit way to distinguish a new structural lifecycle from another publication inside the same lifecycle, without making presentation own controller revision policy; add a test for `loading(A) → loading(B)` where B settles inside its own delay and never inherits A's timer or `Updating…` state.

**Confidence:** high

### Publisher failure is swallowed after structure has already been accepted as ready

**Evidence:** `src/nodus-controller.js` `#publishCurrent()` catches any exception from the injected publisher, logs it, and returns `false`. Its callers do not turn that result into a terminal failure. In particular, `#composeCurrent()` first assigns `this.#state.structure = lifecycle(status, value, error)` and then calls `#publishCurrent()`; a publisher exception therefore leaves the controller's structural state at `ready` (or whatever status was selected) even when presentation failed. `src/nodus-renderer.js` is the production publisher and performs the critical visible-board/Chessground construction during `render()`. `docs/product.md` §Product usability bar says the critical current view requires the visible Root/Line boards to be known **and rendered**, and `docs/components/interface.md` §Requirements says normal `Ready` means the visible Root/Line structure has been established successfully. `test/nodus-controller.test.js` supplies only successful publishers and has no assertion for publication failure.

**Why it matters:** A renderer exception can leave the current view internally classified as structurally ready with only a debug log recording that publication failed. Because the renderer's status presenter runs before later DOM/Chessground work, a publication can also paint the success state and then fail while establishing the rest of the visible graph. The global lifecycle can therefore claim success without the critical rendered neighborhood the product contract defines as usable.

**Suggested next action:** Define publisher failure as an explicit terminal path in the current-view lifecycle (or an equivalent presentation-critical state) rather than ignoring `#publishCurrent()` failure, and add a deterministic controller test with a publisher that throws after structure succeeds to prove the current view cannot remain in the normal success state.

**Confidence:** high
