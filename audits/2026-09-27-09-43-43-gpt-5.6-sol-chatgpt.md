### The Transition contract erases the necessary distinction between recentering and history restoration

**Evidence:** `docs/glossary.md §Transition` defines a Transition as application-level recentering from one Nodus to another. `docs/components/interface.md §Requirements` then states, “A Transition is the only application command that replaces the current Nodus.” But `src/nodus-controller.js::restore(route)` directly replaces `#state.center`, `#state.mode`, and `#state.navDepth` and starts a replacement view without going through `transition()`. This is intentional behavior rather than an accidental bypass: `test/nodus-controller.test.js` has `restore consumes RouteLedger history without writing a new entry`, and `src/route-ledger.js::onRestore` maps native `popstate` into that restore path. Public `transition({ target })` cannot simply replace it because `#recenter()` increments navigation depth and pushes a new browser-history entry.

**Why it matters:** the newly canonicalized language says there is exactly one way the current Nodus changes while the implementation necessarily has two semantically different state changes: creating a new user navigation transition and replaying an already-recorded browser-history state. A maintainer following the contract can either “fix” `restore()` into a history-writing loop or continue bypassing what the docs call the sole replacement command. The abstraction is therefore less honest precisely at the history boundary it is meant to clarify.

**Suggested next action:** make the history distinction explicit before changing code. Either narrow Transition to user/application navigation that creates a new route while documenting history restoration as replay of an existing Nodus state, or define restoration as a kind of Transition and introduce a shared internal recenter operation with an explicit history policy so replay can replace state without pushing a new entry. Do not make `restore()` call the current public `transition()` unchanged.

**Confidence:** high

### Promotion intent is silently collapsed to queen

**Evidence:** `docs/components/interface.md §Requirements` requires that playing a legal Move on the Nodus requests a Transition to the resulting position. In `src/nodus-renderer.js`, Chessground’s center-board `after(from, to)` handler always sends `actions.transition({ move: { from, to, promotion: 'q' } })`. `src/nodus-controller.js::transition()` also defaults omitted promotion to `'q'`. Meanwhile `src/graph.js::legalDestinations()` deduplicates destinations by `from`/`to`, so promotion variants that share the same target square are not represented at the input boundary. `src/move-materialization.js` can accept a specific promotion piece, but the UI has no path to supply knight, rook, or bishop promotion. `test/nodus-transition.test.js` and `test/move-materialization.test.js` cover ordinary `e2-e4` moves but no promotion case.

**Why it matters:** a legal underpromotion entered on the playable Nodus cannot be represented. The application silently interprets the same square-to-square gesture as queen promotion, materializes a different graph edge and target position, and transitions to chess state the user did not choose. This violates both the playable-board promise and the new Move/Transition model.

**Suggested next action:** make promotion choice explicit at the Interface input boundary for promotion moves and pass the selected piece through the Transition request. Treat queen as a UI default only after the user has an opportunity to choose, not as the semantic identity of every promotion. Add deterministic coverage for queen, rook, bishop, and knight promotion reaching distinct expected targets.

**Confidence:** high

### Pure Move resolution now has two owners

**Evidence:** `src/graph.js::moveToChild(sourceKey, move)` already applies a legal move with `chess.js` and returns the canonical target key, playable FEN, SAN, and UCI. Explorer reconciliation in `src/explorer.js::reconcileExplorerSnapshot()` uses that operation. The new `src/move-materialization.js::materializeMove()` independently constructs another `Chess`, applies the move, canonicalizes the resulting FEN, and reconstructs SAN and UCI before doing its persistence work. The duplicate paths already differ: `materializeMove()` defaults promotion to queen while `moveToChild()` uses only the supplied or UCI-encoded promotion.

**Why it matters:** Position Graph now has two implementations of the same chess fact—“what child position and notation does this move produce?”—with different edge behavior. Any later fix to canonical move resolution, promotion handling, notation, or chess.js adaptation must be made twice or Explorer-derived edges and user-materialized edges can diverge. This undercuts the simplification gained by moving materialization out of Discovery.

**Suggested next action:** keep `materializeMove()` as the owner of explicit/manual provenance and persistence, but delegate legal-move resolution and `{ key, fen, san, uci }` derivation to the existing `moveToChild()` graph operation. Then give promotion semantics one owner and test both Explorer and explicit materialization through that shared resolver.

**Confidence:** high

### The new presentation-to-Transition wiring has no automated contract coverage

**Evidence:** `docs/components/interface.md §Verification` requires coverage for “Transition to a known target by mini-board click” and “Transition after a legal Nodus Move.” Those behaviors are wired in `src/nodus-renderer.js`: `[data-nav-key]` and satellite clicks call `actions.transition({ target })`, while Chessground’s `after` callback calls `actions.transition({ move })`. `src/eval-ui.js` adds another target-Transition binding for evidence Rail rows. `test/nodus-transition.test.js` invokes `controller.transition()` directly, and `test/move-materialization.test.js` exercises persistence directly, so neither can fail if renderer event wiring is removed or sends the wrong request. The exact-tip repository tree contains no `nodus-renderer` or browser/DOM contract test; `package.json` uses `node --test` without a DOM/browser test harness.

**Why it matters:** the architectural change deliberately makes presentation emit one canonical application command, but the only automated tests start downstream of that boundary. A regression such as a missing click listener, wrong dataset field, or malformed move request can break the user’s primary navigation path while the new controller and materialization tests remain green.

**Suggested next action:** add the smallest presentation-level contract test that exercises event-to-Transition mapping for at least one miniature-board click and one center-board move. Prefer a narrow binding seam or lightweight browser/DOM fixture over introducing a general browser abstraction solely for testing.

**Confidence:** high
