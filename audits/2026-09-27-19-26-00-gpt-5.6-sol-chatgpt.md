## Findings

### 1. A pending promotion chooser keeps the old orientation after Flip

**Lens:** code — incomplete state coverage / missing regression coverage.

**Evidence:** `src/promotion-chooser.js::choose()` captures `orientation` in the pending state, and `render()` always computes each promotion square from `state.orientation`. Its public `sync` surface accepts only `center` (`sync: (center) => render(center)`), so a same-center refresh cannot update the stored orientation. `src/nodus-renderer.js::render()` builds the new Chessground with the current `view.orientation` and then calls only `promotionChooser.sync(view.center)`. `src/nodus-controller.js::flip()` changes orientation while keeping the same center and republishes the view. The chooser overlay is appended to `#center-board`, while the Flip control remains in the topbar, so Flip is reachable while the chooser is pending. `test/promotion-chooser.test.js` exercises same-center recreation but never changes orientation; its placement cases cover only `color === orientation`, leaving the opposite-orientation placement branch unprotected.

**Why it matters:** after opening promotion and pressing Flip, Chessground renders the board in the new orientation but the recreated promotion choices are laid out using the old one. For a white `e8` promotion this moves the chooser to the wrong displayed file and wrong promotion edge after a flip, breaking the spatial meaning that motivated the board-native chooser.

**Suggested next action:** make pending chooser synchronization consume the current orientation (and any other placement inputs that may change), or explicitly cancel a pending chooser when orientation changes. Add a deterministic regression that opens promotion, flips orientation on the same center, and verifies destination-file and promotion-edge placement for the opposite-orientation branch.

**Confidence:** high.

### 2. The coordinate fix is wired to an entrypoint that current `main` has replaced

**Lens:** change-set — required companion integration is missing.

**Evidence:** current `main` loads `/src/main.ts` from `index.html`, contains the TypeScript entrypoint `src/main.ts`, defines `tsconfig.json`, exposes `npm run typecheck`, and runs that typecheck from both CI and Pages. The audited `choky` tree instead still loads `/src/main.js`, has no `src/main.ts` or `tsconfig.json`, and its workflow/package versions omit the typecheck gate. The coordinate-label repair is imported only by `src/main.js` as `./chessground-overrides.css`. The branch and current `main` have diverged from merge base `8222b230…`, so this is not a simple fast-forward landing surface.

**Why it matters:** resolving the branch against current `main` by keeping the new TypeScript entrypoint without deliberately carrying over the CSS import would silently lose the coordinate repair; resolving in the other direction would regress the TypeScript entrypoint and its verification gate. The promotion work is therefore not integration-ready against the current project-policy/main tree even though its branch preview builds successfully in isolation.

**Suggested next action:** integrate current `main` into `choky` before attempting to ship the branch, preserve `main.ts`, `tsconfig.json`, and the typecheck steps, and carry the Chessground override import into the surviving TypeScript entrypoint. Then rerun deterministic tests, typecheck, Pages build, and the promotion preview.

**Confidence:** high.
