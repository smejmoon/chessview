## Findings

### Renderer fallback still emits the retired composition shape

**Evidence:** `src/visible-graph.js` now defines `VisibleComposition` and `result()` as exactly `{ nodes, relationships, families }`, and `test/graph.test.js` explicitly asserts those are the only top-level keys. `backlog/2026-09-27-visible-composition-contract.md` likewise states that this is the canonical shape. But unchanged `src/nodus-renderer.js` still builds its loading/empty fallback in `emptyStructure(center)` as `composition: { center, direction: 'lines', nodes: [], relationships: [], families: [] }`.

**Why it matters:** The migration leaves two production representations of the same `composition` slot: source-produced values use the new contract while the renderer-local fallback still advertises the legacy context fields. That keeps the ambiguity the change is meant to remove alive during loading/absent-structure states and gives future presentation code a plausible place to re-learn the obsolete fields.

**Suggested next action:** Update the renderer fallback to use only the canonical three-field composition value, and add or extend a loading/fallback regression test so presentation cannot silently reintroduce `center` or `direction` on `composition`.

**Confidence:** high.

### Family metadata preservation no longer matches the implemented decision

**Evidence:** The tracked outcome's `Edges:` says to preserve current "merge/family metadata." At the base revision, Line families were created with `{ direction: 'lines', lineShare, rootEdgeId }`, and Root families with `{ direction: 'roots', rootEdgeId }`, with Root direction also propagated to inherited families in `src/graph.js`. On `koko`, `src/visible-graph.js` intentionally omits those `direction` properties, and `test/graph.test.js` now asserts a Line family value without `direction`. At the same time, the change moves direction context to the Nodus view: `src/root-presentation.js` passes `view.mode` explicitly to `drawVisibleEdges`, and `src/map-render.js` requires that direction argument. A repository search at the base found no `family.direction` consumer.

Right Place conclusion: `finding: keep`; `boundary: confirmed`. The evidence supports the architectural removal of duplicated direction context, so the defect is not automatically "restore `family.direction`". The defect is that the changed tracker still promises preservation of family metadata while the implementation and tests deliberately retire one such field.

**Why it matters:** The completion contract has two incompatible readings. A future close can either treat the field removal as completed simplification or as a regression against the preserved-metadata edge, with no durable statement settling which interpretation binds.

**Suggested next action:** Make the tracked contract explicit before close: if family `direction` is intentionally retired because view mode owns that context, narrow the preservation statement accordingly; otherwise restore the metadata and its assertions. Keep the code and completion text on one decision.

**Confidence:** high.

### Verification is blocked by dispatch access, not by absence of a repository execution path

**Evidence:** `backlog/2026-09-27-visible-composition-contract.md` says verification is blocked "until a repository execution path is available" for `npm test`, `npm run typecheck`, and `npm run build`. But `.github/workflows/ci.yml` already exposes `workflow_dispatch`, and its `Verify` job runs `npm ci` followed by exactly those three verification commands on Node 24. The current connected ChatGPT tool surface did not expose a workflow-dispatch action, which explains why this audit cannot start the run, but that is an executor-access limitation rather than absence of a repository execution path.

**Why it matters:** Backlog's owner requires `Blocked:` to name an exact, independently observable condition. As written, the entry can remain blocked for a condition that is already false, and a cold reader is not told the concrete handoff that can clear verification.

**Suggested next action:** Rewrite the blocker/step around the actual dependency: dispatch the repository's CI workflow manually for the exact `koko` tip (or supply equivalent execution evidence), while noting that the current connected ChatGPT environment cannot perform that dispatch itself.
