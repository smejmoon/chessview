## Findings

### Reset Pages can resurrect a cleaned preview

**Evidence:** `chatgpt/branch-preview.md` §Cleanup still defines `cleanup` as removing task-branch preview state, without deleting the source branch. The new `docs/components/delivery.md` §Pages reset instead makes branch existence the retention rule: every undeleted non-`main` branch is rebuilt into the next reset snapshot. Therefore a branch whose preview was successfully cleaned but whose Git ref still exists will be republished by the next `reset-pages` run.

**Why it matters:** the lifecycle's terminal cleanup state is no longer stable. A stale preview can become publicly reachable again after unrelated Pages maintenance, and the two maintained command contracts disagree about whether an existing-but-cleaned branch should have a preview.

**Suggested next action:** settle the lifecycle rule in one owner before merge. Either make branch retirement part of the cleanup contract, or preserve an explicit notion of preview-active branches that Reset Pages consumes; then have the other command point to that owner rather than leaving preview removal and branch-existence retention in conflict.

**Confidence:** high

### Live branch builds inherit repository-write credentials

**Evidence:** `.github/workflows/reset-pages.yml` grants the whole `reset` job `contents: write`, uses `actions/checkout@v5` without disabling persisted credentials, then enters every live branch worktree and executes that branch's `npm ci`, `npm run typecheck`, and `npm run build`. Exact-target run `36409557061` confirms `Contents: write`, `persist-credentials: true`, and a GitHub authorization extraheader before those branch commands run. Yet `docs/components/delivery.md` §Pages reset states that the reset force-updates only `gh-pages` and does not rewrite or delete `main` or task branches.

**Why it matters:** a still-existing branch controls its package lifecycle and npm script commands. During reset, that branch code runs with a persisted repository-write Git credential, so the workflow does not enforce the documented `gh-pages`-only write boundary; branch code can attempt writes to any ref the token permits. The push-triggered dry-run has the same credential exposure even though its final `gh-pages` push is skipped.

**Suggested next action:** run branch discovery, install, type-check, build, and snapshot assembly in a `contents: read` job with no persisted write credential. Hand the completed snapshot to a separate publication-only job that has `contents: write` and performs only the final `gh-pages` replacement, with no source-branch scripts executed under that authority.

**Confidence:** high
